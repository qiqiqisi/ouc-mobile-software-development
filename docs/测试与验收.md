## 本次修复的主要问题

- 首页切换分类时，较慢的旧请求可能覆盖新分类内容；现使用请求序号隔离。
- 个人主页最多显示 100 条旧帖子；现使用连续分页读取，并单独获取发布总数。
- 点赞/收藏快速连点或网络重试可能造成状态翻转、重复计数；现提交明确目标状态并使用唯一关系 ID 与事务。
- 点赞请求失败时恢复原始按钮状态和计数；首页返回时通过增量同步保留已有列表。
- 评论发送失败保留草稿，同一内容重试复用请求 ID；旧评论列表请求不能覆盖新列表。
- 历史访问重复记录、按账号隔离、删除笔记后的失效条目、清空时新访问被误删均有处理。
- 多图上传后续失败时，已上传的前几张图片原先不会被调用方拿到，导致无法回滚；现由上传工具清理部分成功的文件。
- 发布时固定提交快照并锁定封面切换，防止上传期间表单变化使封面索引错配。
- 首次并发登录使用创建操作，避免覆盖已有用户资料与计数。
- 更新昵称头像时同步帖子和评论作者快照；同步失败则保留旧头像，避免引用失效。
- 云函数拒绝引用其他用户上传的图片/头像；删除笔记时只清理属于作者路径的云文件。

## 数据与性能边界

- 收藏、点赞、关注、评论、历史均通过云函数持久化；没有加入冒充真实数据的本地演示模式。
- 所有列表每页默认 20 条，服务端最多 50 条；清空历史每个云函数请求最多删除 20 条。
- 删除帖子后，关联互动和历史中的失效引用不会显示。底层失效关系文档暂时保留，便于避免批量清理影响其他用户；如以后需要长期运行的垃圾清理，应单独增加管理任务。
- 并发新内容会改变基于页码的列表位置，前端会去重；下拉刷新用于获取最新完整顺序。这不是跨请求固定快照分页。
- 点赞、收藏、关注的即时本地反馈只代表提交中的视觉状态；服务端失败会回滚或提示重试。
